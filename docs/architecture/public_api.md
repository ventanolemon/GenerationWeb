# Публичный API: можно ли сделать из сервиса продукт

Проектный документ. Отвечает на вопрос «можно ли открыть генератор заданий
наружу, как открыты Яндекс.Карты или Google Maps» — и если да, то что для
этого не хватает. Основан на фактическом коде (`web_layer/*.cs`,
`generator_service/`, `core/`), а не на желаемом.

## 1. Короткий ответ

**Можно, и архитектура для этого подготовлена лучше, чем обычно бывает.**
Три вещи уже стоят там, где надо: `web_layer` — единственная точка входа
для всех клиентов (инвариант топологии §6.1), `core/` — headless-движок без
единой зависимости от FastAPI или Qt, а генераторы и узлы графа живут в
реестрах, куда новое добавляется конфигом, а не правкой ядра.

Но «API как у Карт» — это **не префикс `/v1/` над существующими
эндпоинтами**. Карты продают не HTTP-ручку, а связку: ключ приложения,
квота, версионированный контракт с обещанием совместимости, встраиваемый
виджет и консоль разработчика. Движок у нас есть; нет ровно того, что
превращает движок в продукт. Ниже — честный перечень, что есть, чего нет и
в каком порядке это строится.

## 2. Разбор аналогии: из чего на самом деле состоит «API Карт»

| Составляющая | Что это значит | У нас сегодня |
|---|---|---|
| Ключ **приложения** | Субъект — не человек, а стороннее приложение | ❌ идентичность только человеческая (`X-User-Id` = логин) |
| Квоты и тарификация | Учёт вызовов по ключу, лимит, счёт | ❌ ничего |
| Версионированный контракт | `/v1/` живёт годами, ломать нельзя | ❌ DTO повторяют схему БД |
| Стабильные публичные id | Внешние id не равны первичным ключам | ❌ наружу торчат `partition_id`, `subject_id` |
| Встраиваемый клиент | `<script>` + виджет, не только REST | ⚠️ React-вьюхи есть, но не выделены |
| Песочница и консоль | Тестовый ключ, документация, метрики | ❌ ничего |
| Ограничение по домену | Браузерный ключ работает с одного origin | ❌ CORS открыт списком из конфига |

Вывод из таблицы: **работы не в движке, а вокруг него.** Это хорошая
новость — движок и есть самое дорогое, и он готов.

## 3. Что уже готово и переиспользуется как есть

* **Граница.** `web_layer` — ровно то место, где живёт публичный API:
  через него уже ходят и SPA, и десктоп, у него есть кеш справочников,
  Polly-ретраи и типизированный клиент к движку. Новый сервис заводить не
  нужно — это эволюция существующего, тем же ходом, каким `web_layer` стал
  оркестратором (`system_topology.md` §1).
* **Headless-ядро.** `core/` не знает про HTTP, роли и UI. Публичный API —
  ещё один потребитель тех же функций, а не форк логики.
* **Контракт генератора.** `TaskGenerator → StaticTask | InteractiveTask`
  уже абстракция нужного уровня: наружу отдаётся «задание», а не «результат
  работы конкретного генератора физики».
* **Механизм ограничения контента.** Выдачи предметов
  (`subject_grants`, `core/grants_api.py`) — уже готовый ответ на вопрос
  «кому какие предметы доступны». Для публичного API он нужен дословно, с
  заменой субъекта: не «преподавателю выдан предмет», а «ключу выдан
  предмет». Таблица и логика переиспользуются, меняется тип владельца.

## 4. Четыре блокера — и почему каждый настоящий

### 4.1. Нет субъекта «приложение»

Сегодня единственная идентичность — человек: `X-User-Id` с логином, роль
из `X-User-Role`, причём даже JWT ещё не введён (auth-фаза `web_layer` не
пришла — см. `rbac_and_data_model.md`). Стороннее приложение — это другой
вид субъекта: у него нет роли, ФИО и группы, у него есть **владелец,
скоуп и квота**.

Значит нужны свои таблицы, а не запись в `users`:

```sql
api_clients (id, name, owner_user_id, created_at, status)
api_keys    (key_hash PK, client_id, kind 'server'|'browser',
             allowed_origins, created_at, revoked_at)
api_usage   (client_id, day, endpoint, calls)      -- учёт для квоты
```

Ключ хранится **хэшем**, как пароль: утечка дампа не должна отдавать
рабочие ключи. Браузерный ключ отдельного вида — он по определению
публичен (лежит в исходнике страницы), и защищает его не секретность, а
привязка к origin.

### 4.2. Наружу торчит внутренняя схема

`GET /api/subjects` отдаёт `id` строки таблицы `Subjects`; `/api/generate`
принимает `partition_id`; в разделах наружу уезжает `constracted` —
внутреннее число, где «4 значит граф». Публичный контракт такое обещать не
может: перенумеруется таблица — сломаются все интеграции, а `constracted`
придётся поддерживать вечно, включая его историю.

Нужен слой публичных идентификаторов и словарей: стабильный `slug`/UUID
вместо первичного ключа и `"kind": "graph" | "test" | "single"` вместо
числа. Это не косметика — это то самое обещание совместимости, ради
которого версия и ставится в путь.

### 4.3. Ни квоты, ни лимита

Генерация — не бесплатная операция: за ней исполнение графа, а за
контуром (`/api/contour/jobs`) — вызовы внешних LLM за реальные деньги.
Публичный ключ без квоты — это открытый кран к чужому бюджету, и первая же
ошибка в чужом цикле `for` его выпьет. Квота — не «этап потом», а условие
самого открытия.

### 4.4. Интерактивные задания не переживают горизонтальное масштабирование

Найдено в коде, и это самый неочевидный блокер.
`generator_service/session_store.py` держит живые `InteractiveTask` в
**in-memory dict, по одному на процесс uvicorn** (там это прямо написано в
докстринге и честно оговорено). Пока инстанс один — работает. Публичный API
живёт за балансировщиком: второй запрос той же сессии придёт в другой
процесс и не найдёт её.

Лечится одним из двух: вынести состояние сессии в общее хранилище
(Postgres/Redis) — или сделать интерактив stateless, отдавая клиенту
подписанный курсор состояния. Второе честнее для публичного API (сервер без
памяти о клиенте масштабируется линейно), но требует, чтобы состояние
тренажёра сериализовалось.

> **Сделано (этап 4):** выбран первый вариант — общее хранилище. Второй
> опирается на то же самое снятие состояния, но добавляет подпись и возню с
> размером курсора, а выигрывает лишь на масштабе, которого ещё нет.
> Ключевая часть — сериализуемость состояния — теперь есть
> (`InteractiveTask.state()`), и переход на stateless-курсор из этой точки
> уже локальный.

### 4.5. Бонусом: два разных формата ошибок

`generator_service` (FastAPI) отвечает `{"detail": "..."}`,
`web_layer` — `{"error": "..."}`. Внутри это терпимо, наружу — нет:
у публичного API один конверт ошибки, с машинно-читаемым кодом:

```jsonc
{ "error": { "code": "quota_exceeded", "message": "…", "request_id": "…" } }
```

Унификация дешёвая и делается до всего остального, иначе её потом
придётся ломать вместе с версией.

## 5. Предлагаемая форма

**Две поверхности, а не одна.** `/api/*` остаётся внутренним — он служит
своему SPA, меняется вместе с ним и ничего никому не обещает. `/api/v1/*`
— публичный, с обещанием совместимости. Их нельзя объединять именно
потому, что у них разные обязательства: внутренний хочется менять быстро,
публичный нельзя менять вовсе.

```mermaid
flowchart LR
    EXT["Стороннее приложение\n(сервер или браузер)"]
    OWN["Свой SPA + десктоп"]
    WL["web_layer\n/api/*  — внутренний\n/api/v1/* — публичный:\nключ · квота · скоуп · версия"]
    GS["generator_service\n(внутренняя сеть)"]
    CS["contour_service"]

    EXT -->|"Bearer api_key"| WL
    OWN -->|"сессия пользователя"| WL
    WL --> GS
    WL --> CS
```

Минимальный продуктовый набор ручек — четыре, и они же покрывают 90 %
сценариев встраивания:

```
GET  /api/v1/catalog              что доступно этому ключу
POST /api/v1/tasks                сгенерировать задание   ← основная
POST /api/v1/tasks/{id}/answer    проверить ответ / ход интерактива
POST /api/v1/exports              набор вариантов (уже есть внутри)
```

`POST` — с заголовком `Idempotency-Key`: генерация тарифицируется, и
повтор после сетевого обрыва не должен списывать второй раз.

**Встраиваемый виджет** — отдельный слой поверх REST, не вместо него:
`<script src=".../v1/embed.js">` + iframe. React-вьюхи для этого уже
существуют и уже развязаны (`StaticTaskView`, `InteractiveTaskView`,
`BlockRenderer` с реестром блоков) — виджет их переиспользует, а не
переписывает.

## 6. Порядок работ

| Этап | Содержание | Продуктовых решений требует | Статус |
|---|---|---|---|
| 0 | Единый конверт ошибки; заморозить DTO; OpenAPI-описание | нет | **сделано** |
| 1 | `api_clients`/`api_keys`, `Bearer`-аутентификация, скоуп контента через выдачи | да: кто заводит ключи | **сделано** |
| 2 | Учёт вызовов, квота, rate limit, `Idempotency-Key` | да: тарифы | **частично** |
| 3 | Публичные id/словари вместо `partition_id`/`constracted` | нет, но ломает клиентов — только с `/v1/` | **сделано** |
| 4 | Сессии интерактива вне памяти процесса | нет | **сделано** |
| 5 | `embed.js`, песочница, консоль разработчика | да: продукт целиком | — |

Этапы 0 и 4 сделаны первыми именно потому, что не требуют ни одного
продуктового решения и полезны сами по себе, даже если публичного API не
будет. Этапы 1–3 сделаны следом: продуктовое решение «кто заводит ключи»
разрешилось само собой — админ, как и всё остальное административное в
сервисе, а самообслуживание разработчиков относится к этапу 5.

### Что вошло в этапы 1–3

Поверхность (`generator_service/routers/public_v1.py`):

```
GET  /v1/me                      кто я, сколько квоты осталось
GET  /v1/catalog                 что доступно этому ключу
POST /v1/tasks                   сгенерировать задание   ← основная
POST /v1/tasks/{session}/answer  ход интерактивной сессии
```

Управление — `/admin/api-clients/*` (admin-only): завести приложение,
выпустить и отозвать ключ, назначить скоуп, квоту и статус.

**Ключи** (`core/api_clients.py`). `gw_live_…` / `gw_web_…`, 256 бит из
`secrets.token_urlsafe`; в базе — sha256-хэш и открытый префикс для
опознания в списке. Быстрый хэш вместо pbkdf2, которым в этом же проекте
хэшируются пароли, — осознанно: пароль выбирают из крошечного словаря, и
медленный KDF покупает время против перебора; ключ перебирать нечего ни за
какое время, зато проверяется он на каждом запросе. Отказ не различает
«нет такого ключа» и «ключ отозван» — иначе перебор получил бы оракула.

Браузерному ключу обязателен `allowed_origins`: он лежит в исходнике
страницы и секретом не является, привязка к origin — единственное, что его
ограничивает.

**Скоуп.** Пустой набор явных выдач = клиенту доступны все встроенные
предметы (`owner_user_id IS NULL`) и только они — тот самый безопасный
старт из §8: встроенные принадлежат продукту, авторский контент
преподавателей наружу без явного решения администратора не уходит. Явные
выдачи (`api_client_subjects`) набор замещают. Это та же механика, что
`subject_grants` у преподавателя, с другим субъектом.

«Темы нет» и «тема есть, но не для этого ключа» отвечают ОДИНАКОВО: иначе
перебором публичных id можно было бы выяснить, что существует у других
клиентов.

**Публичные id.** `Subjects.public_id` / `Partitions.public_id` — uuid,
проставлен миграцией существующим строкам и лениво новым (пути вставки —
bootstrap, sync, CRUD — о поле не знают, и править их все ради одного
потребителя было бы лишним риском). Наружу не уходит ни `partition_id`, ни
`constracted`: тип темы — словарное слово (`single`/`constructor`/`group`/
`test`/`graph`). Внутренний `partition_id` вычищается даже из `meta`
задания — иначе схема утекала бы с чёрного хода.

**Квота — только техническая часть этапа 2.** Счётчик на (клиент, сутки
UTC), суточный лимит на клиенте, 429 при исчерпании. Инкремент до работы, а
не после: иначе параллельные запросы проскочили бы лимит разом.
Тарифицируется только генерация — каталог и `/me` бесплатны, брать за них
значило бы наказывать за аккуратную интеграцию, которая сверяется с
каталогом. `Idempotency-Key` и тарификация не сделаны: они и есть та часть
этапа 2, которой нужны тарифы.

**Граница сети.** `generator_service` остаётся внутренним; наружу смотрит
`web_layer`, релеящий `/api/v1/*` (`PublicApiEndpoints.cs`). Ключ
проверяется НЕ в релее: проверка неотделима от скоупа контента, а тот живёт
в одной БД с каталогом — разнеси их, и на каждый вызов пришлось бы ходить
в базу дважды из двух сервисов ради одного решения. Тело ответа релей не
трогает: у `/v1` свой конверт ошибки, и переписывать его по дороге значило
бы его сломать.

Три вещи в релее сделаны иначе, чем у внутренних прокси, и каждая — не
украшение:

* **Своя политика CORS** (`public-v1`): любой origin, без credentials,
  `X-Request-Id` в `WithExposedHeaders`. Под умолчательную политику
  (список origin'ов SPA плюс `AllowCredentials`) чужое приложение не
  подходит по определению, и браузерный ключ `gw_web_…` не работал бы
  вовсе — браузер отбил бы запрос до того, как сервис увидел ключ.
  Ограничение по домену от этого не исчезает, оно просто в правильном
  месте: `allowed_origins` КЛЮЧА. CORS браузерный и обходится любым
  не-браузером; привязка ключа — нет.
* **`X-Request-Id` возвращается в ответе.** Прямой проброс без обратного
  бесполезен: свой идентификатор интегратор и так знает, а когда он его не
  прислал, сервис сгенерировал свой — и тот остался бы только в наших
  логах. «Сообщите X-Request-Id» превратилось бы в «сообщите примерное
  время».
* **POST в `/v1` не ретраится.** Квота списывается ДО работы (иначе
  параллельные запросы проскочили бы лимит), и Polly-повтор после 5xx
  списал бы её второй раз: интегратор платил бы за наш сбой, тем больше,
  чем хуже нам. Тот же довод, по которому ретраев нет у клиента контура.

> Собрать `web_layer` в этой среде нечем: `dotnet` в контейнере нет, а
> хост дистрибутива закрыт политикой egress. Изменения выше проверены
> чтением против контракта сервиса (состав `/v1/*`, конверт ошибки,
> заголовок из `generator_service/errors.py`), но **не компилировались** —
> это надо сделать на машине с .NET SDK перед выкаткой.

### Что вошло в этап 0

`generator_service/errors.py` — конверт
`{error: {code, message, request_id}}` на всех ошибках сервиса, включая
необработанные исключения (наружу уходит без подробностей, подробности в
лог). Коды стабильны и привязаны к статусу; `X-Request-Id` проходит
насквозь для корреляции с логом.

Два решения по совместимости:

* **`detail` оставлено** рядом с `error.message`. Десктопные клиенты
  (`core/grants/client.py`, AdminClient) читают из тела именно его —
  выкинуть поле значило бы заменить объяснение ошибки на «HTTP 403».
  Помечено устаревшим, снимается вместе с обновлением десктопа.
* **Формат `web_layer` не тронут.** Там ошибка — `{error: "строка"}`, и её
  так и читает SPA (`String(body.error)` в `frontend/src/api/client.ts`).
  Превращать `error` в объект без правки фронта нельзя, а править фронт
  ради внутреннего API незачем: единый конверт — обещание ПУБЛИЧНОЙ
  поверхности, и вводить его в `web_layer` следует вместе с `/api/v1`.

Заморозка форм — `core/test_api_contract.py`: ключи ответов перечислены
поимённо, любое молчаливое переименование роняет сборку. Это и есть
работающая заморозка; замороженный на бумаге контракт живёт до первого
рефакторинга. Выгрузка описания — `python -m scripts.export_openapi`
(файл не коммитится: он порождается из кода и разошёлся бы с ним).

### Что вошло в этап 4

Состояние сессии снимается самим заданием
(`InteractiveTask.state()`/`restore()` — пара необязательная, умолчание
`None` значит «жить только в памяти») и хранится в `interactive_sessions`
(миграция 007). `SessionStore` стал двухуровневым: кеш живых объектов в
процессе + снимок в БД, промах кеша поднимает сессию через пересборку
задания из партиции. Персист — улучшение, а не условие работы: отказ БД
логируется, текущий ход пользователя не роняется.

## 6.1. Что осталось незакрытым

Честный список на сегодня:

* **`Idempotency-Key` не реализован.** Повтор `POST /v1/tasks` после
  сетевого обрыва спишет вторую единицу квоты. Пока квота — техническое
  ограничение, а не деньги, цена ошибки невелика; с появлением тарифов это
  становится обязательным.
* **Rate limit (запросов в секунду) нет** — есть только суточная квота.
  Всплеск в тысячу запросов за секунду квоту не нарушит, а сервису
  повредит. Лечится на уровне `web_layer`, где уже есть место под лимиты
  соединений.
* **Релей `web_layer` не скомпилирован** — в окружении разработки не было
  .NET SDK. Код написан по образцу существующих прокси
  (`ProxyRelay`/`ProxyAsync`), но собран и проверен не был; перед выкаткой
  нужен `dotnet build`.
* **Учёт — счётчик, а не журнал.** Для квоты достаточно суммы; для
  тарификации и разбора инцидентов понадобится журнал вызовов — это
  отдельная таблица с другим сроком жизни.

## 7. Чего делать не надо

1. **Не открывать `generator_service` наружу.** Он спроектирован
   внутренним. Запись и чтение авторского содержимого разделов теперь
   авторизованы (`core/content_authz.py`, см. `rbac_and_data_model.md` §3),
   но витрина (`/subjects`, `/subjects/{id}/partitions`) остаётся открытой
   сознательно — по ней ходит решающий задачи гость. Публичный вход —
   только через `web_layer`.
2. **Не строить публичный API поверх схемы БД один в один** — см. §4.2.
   Один раз пообещав `partition_id`, его придётся хранить вечно.
3. **Не начинать с биллинга.** Сначала учёт и квота (этап 2), деньги —
   после того как есть что считать.
4. **Не вводить GraphQL и брокер сообщений.** Четыре ручки — не тот объём,
   на котором GraphQL окупается; для длительных операций уже выбрана
   job-очередь в Postgres с поллингом (`system_topology.md` §4), и менять
   это решение публичный API не заставляет.

## 8. Риск, который стоит назвать вслух

Технически открыть API можно. Но контент, который через него поедет, —
**авторский**: разделы и графы создают преподаватели, и `Subjects` уже
хранит `owner_user_id`. Отдавать их сторонним приложениям — вопрос прав на
контент, а не инженерии. Механика для разграничения есть (выдачи), решение
«что вообще доступно наружу» — продуктовое и правовое.

Безопасный старт, снимающий вопрос целиком: открывать наружу **только
встроенные code-предметы** (`owner_user_id IS NULL`) — они принадлежат
самому продукту, а не преподавателям. Авторский контент подключать
отдельным явным согласием автора, и лучше — уже после того, как публичный
API докажет спрос.
