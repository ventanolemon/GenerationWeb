# Развёртывание

Пример на четыре контейнера. Он рабочий и на нём можно поднять установку
для группы, но у него есть границы — они описаны ниже честно, в отдельном
разделе, а не спрятаны.

## Запуск

```bash
cd deploy
cp .env.example .env      # и отредактировать — там пароли и ключи
docker compose up --build
```

Открывается на `http://localhost:8080` (порт — `PUBLIC_PORT` в `.env`).

Первая сборка долгая: ставится PyQt6 с зависимостями, `npm ci` и
`dotnet restore`. Дальше пересобирается только изменившийся слой.

## Из чего это состоит

```
      браузер / десктоп
             │  :8080
        ┌────▼─────┐
        │  nginx   │  статика клиента + единственный путь к /api
        └────┬─────┘
             │  :8080
        ┌────▼─────┐
        │   web    │  ASP.NET: разбирает сессию, назначает роль
        └──┬────┬──┘
    :8000  │    │  :8001
   ┌───────▼─┐ ┌▼──────────┐
   │generator│ │  contour  │  FastAPI, приватная сеть
   └────┬────┘ └─────┬─────┘
        └─────┬──────┘
        ┌─────▼─────┐
        │   том     │  рабочая база (`/data`)
        └───────────┘
```

Наружу торчит **только nginx**. У `generator` и `contour` в
`docker-compose.yml` нет ни одного проброшенного порта, и это не
экономия: личность приходит к ним заголовками `X-User-Id`/`X-User-Role`,
которые ставит `web` после проверки сессии. Достучись до них браузер
напрямую — он ставил бы эти заголовки сам, и роль перестала бы что-либо
значить. Тот же заслон продублирован в nginx: заголовки личности,
пришедшие снаружи, срезаются на входе.

### Почему Python-образ один на две службы

Обе службы живут в одном монорепо, тянут один `requirements.txt` и
импортируют одно ядро. Два образа отличались бы только строкой запуска —
то есть не отличались бы ничем, кроме шанса разъехаться по версиям.
Разная у них команда, а не сборка.

### Почему в образе есть Qt

`core/rendering.py` — общий код с десктопом, и на сервере он тоже рисует:
формулы, графики, картинки в заданиях. PyQt6 не импортируется без
`libgl1`, `libxkbcommon0` и остальных из `python.Dockerfile`, поэтому они
там и стоят. Дисплея нет — работает `QT_QPA_PLATFORM=offscreen`.

## Данные

Рабочая база лежит **на томе**, а не в образе.

Это не деталь упаковки, а причина, по которой поставка и данные вообще
были разделены. Слой образа доступен только на чтение; пока база лежала
в `resources/`, служба писала бы в файл, который раздаётся пользователям,
и в контейнере просто не запустилась бы.

Как это работает: `resources/users_database.db` в образе — **шаблон**.
При первом запуске `const.ensure_data_dir()` копирует его в
`$GEN_DATA_DIR` (том, `/data`). Дальше шаблон не трогается никогда, а
существующая база не перезаписывается — обновление образа накопленного не
теряет.

```bash
docker compose down             # данные на месте
docker compose down --volumes   # данные снесены, при следующем старте
                                # том наполнится из шаблона заново
```

## Учётные записи

На свежем томе есть организация по умолчанию и администратор
развёртывания — их заводит сама служба при старте. Служебные аккаунты
ставятся отдельно:

```bash
docker compose exec generator python -m scripts.seed_accounts \
    --dev-password 'СВОЙ-ПАРОЛЬ' \
    --owner-password 'СВОЙ-ДРУГОЙ-ПАРОЛЬ' \
    --reset-password
```

**Пароли по умолчанию лежат в репозитории открытым текстом.** Скрипт
говорит об этом при каждом запуске, и здесь это повторено намеренно:
развёртывание без смены паролей — это установка, в которую войдёт
администратором любой, кто читал исходники.

## Демо-наполнение

Пустая установка — это рабочая установка, а не поломка: предметы и
разделы приезжают из поставки, заданий у неё нет. Чтобы посмотреть
интерфейсы на данных:

```bash
docker compose exec generator python -m scripts.seed_demo
```

## Куда это не годится

Список границ, а не оговорок. Каждая из них — то, за что придётся взяться
до боевой нагрузки.

1. **Очередь контура на SQLite.** Обе Python-службы держат один файл на
   одном томе. Это работает, пока воркер один и хост один. Второй воркер
   или второй хост — нужен Postgres: `CONTOUR_PG_DSN` в `.env`,
   `pip install 'psycopg[binary]'` в образ. `PostgresJobQueue` берёт
   задания через `FOR UPDATE SKIP LOCKED` и рассчитан ровно на это.

2. **Общий том между контейнерами.** SQLite по сети (NFS, сетевой том)
   ломается на блокировках. Пока это `local`-том одного хоста — всё
   честно; при разъезде по узлам база должна переехать в Postgres вместе
   с очередью.

3. **TLS здесь нет.** Наружу смотрит `http://`. Перед выкладкой в
   интернет нужен обратный прокси с сертификатом (или `certbot` в этот
   же nginx) и `PUBLIC_ORIGIN=https://…` — иначе токен сессии ездит
   открытым текстом.

4. **Токен сессии клиент хранит в `localStorage`.** Это известное
   решение, отложенное осознанно: переход на httpOnly-cookie тянет за
   собой защиту от CSRF, а требования к ней ещё не сформулированы.
   XSS в клиенте здесь означает угон сессии.

5. **Резервных копий нет.** Том переживает `down`, но не переживает
   удаление. Копия базы — обычный `docker compose exec generator
   sqlite3 /data/users_database.db ".backup /data/backup.db"` по
   расписанию, но расписания в этом примере нет.

6. **Одна реплика каждой службы.** `restart: unless-stopped` поднимает
   упавший контейнер, но обновление образа — это простой на время
   пересборки. Плавной выкатки в примере нет.

## Проверка руками

```bash
curl -sf http://localhost:8080/healthz                  # nginx жив
docker compose exec generator \
    python -c "import urllib.request; print(urllib.request.urlopen(
        'http://127.0.0.1:8000/health').read())"        # ядро собрало генераторы
curl -s http://localhost:8080/api/subjects | head -c 200   # весь путь целиком
```

Третья команда — самая важная: она проходит nginx → web → generator, то
есть ровно тот путь, по которому ходит браузер. Первые две отвечают за
свой узел и молчат о соседях.
